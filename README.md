# Aperio | Бесплатные мероприятия

Чат-бот и мини-приложение в MAX. Трек «Досуг и развлечения».

## Назначение

Сообщает, когда открывается запись на бесплатные экскурсии, лекции и мастер-классы в Москве, и показывает, в какие дни можно в музей бесплатно по льготе пользователя.

## Основной сценарий

1. `/start` в боте → кнопка «Открыть Aperio».
2. Выбор категории льготы (можно пропустить).
3. Главная: льготные дни и окна записи с полосой сроков.
4. Каталог → фильтры → «Уведомлять о таком» (фильтр становится подпиской).
5. Карточка: сердечко — напоминание, «Позвать компанию» — ссылка в чат MAX.
6. При открытии записи бот присылает уведомление.

Проверка без ожидания: `/demo` или «Прислать тестовое уведомление» в профиле — окно откроется через 60 секунд.

## Архитектура

| Компонент | Путь | Роль |
|---|---|---|
| web | `app/web.py`, `app/templates` | Страницы, формы, админка, проверка `initData`, схема и начальные данные |
| Запуск в один контейнер | `app/run.py` | Для хостинга, который поднимает один контейнер: web, затем bot и worker. В `compose` не используется |
| bot | `app/bot.py` | Команды `/start`, `/demo`, `/admin`, `/reply`, `/help`; long polling через maxo |
| worker | `app/worker.py` | Уведомления: запись открылась, закрывается завтра, событие завтра, льготный день завтра |
| Домен и данные | `app/domain.py`, `app/services.py`, `app/schema.sql`, `app/seed.py` | Правила повторения, запросы, схема, начальные данные |

Виды льготных правил: «n-й день недели месяца», «последний день недели месяца», «Московская музейная неделя» (день внутри третьей календарной недели) и «каждую неделю». Даты считаются на любую глубину, вести их вручную не нужно.

Стек: Python 3.12, FastAPI + Jinja2, asyncpg, PostgreSQL 16, maxo 0.9.

Схемы: [архитектура](docs/schemes/01-architecture.svg), [пользовательский путь](docs/schemes/02-user-flow.svg), [схема данных](docs/schemes/03-data.svg), [механика уведомлений](docs/schemes/04-notifications.svg).

## Внешние сервисы и интеграции

Собственного публичного API у проекта нет: мини-приложение отдаёт готовые страницы, наружу не смотрит никто, кроме бота. Всё, к чему мы подключаемся, — в таблице.

| Сервис | Что делаем | Где в коде | Авторизация | Если сервис недоступен |
|---|---|---|---|---|
| **MAX Bot API** (`botapi.max.ru`) | Получаем обновления long polling'ом, отправляем сообщения и кнопки, ставим список команд | `app/bot.py`, `app/messages.py`, `app/worker.py` | `MAX_BOT_TOKEN` из окружения | `bot` и `worker` повторяют попытку; отправка уведомления снимает бронь в `notifications` и повторяется на следующем проходе. `web` продолжает работать — интерфейс не зависит от бота |
| **MAX Bridge** (`st.max.ru/js/max-web-app.js`) | Получаем `initData` при запуске мини-приложения, `start_param` для диплинков, `shareMaxContent` для «Позвать компанию», `BackButton`, `HapticFeedback` | `app/templates/base.html`, `app/static/js/app.js` | — | Скрипт не загрузился → страница остаётся рабочей, `shareMaxContent` заменяется копированием ссылки в буфер |
| **PostgreSQL 16** | Единственное хранилище | `app/db.py` | `POSTGRES_*` | `web` не стартует: пул поднимается на старте вместе с миграциями |
| **cloudflared** (профиль `tunnel`, только локально) | Временный HTTPS-адрес для проверки мини-приложения без хостинга | `compose.yaml` | — | На хостинге не запускается |

Внешних источников данных о мероприятиях мы не подключаем сознательно — обоснование в разделе «Ограничения». Исходящих запросов, кроме MAX Bot API, приложение не делает: контейнерам достаточно доступа к `botapi.max.ru` и к базе.

Персональные данные наружу не уходят. В MAX отправляются только тексты уведомлений тому пользователю, который сам подписался.

## Запуск

```bash
cp .env.example .env      # заполнить MAX_BOT_TOKEN и MAX_BOT_USERNAME
docker compose up --build
```

Временный HTTPS для мини-приложения: `docker compose --profile tunnel up --build`, адрес — в логах сервиса `tunnel`. Его же указать в кабинете MAX: Чат-боты → ⋮ → Настройки → Мини-приложение.

Остановка: `docker compose down` (данные сохранятся), `docker compose down -v` (удалить данные).

## Постоянный адрес мини-приложения

MAX требует HTTPS. Туннель `cloudflared` даёт временный адрес и подходит только для проверки: при перезапуске он меняется.

Постоянный адрес — домен сервера. На Timeweb Cloud это **App Platform**; к приложению сразу привязывается бесплатный технический домен вида `имя.twc1.net`, Nginx и Let's Encrypt настраиваются сами. Этот адрес и нужно указать в настройках бота MAX: Чат-боты → ⋮ → Настройки → Мини-приложение. Свой домен можно привязать позже, сертификат выпустится автоматически.

Переменные (`MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`, `ADMIN_USER_IDS` и прочие) задаются в панели App Platform — файл `.env` в репозиторий не коммитится.

Дальше всё зависит от того, каким типом приложения создан сервис. Вариантов два, и они требуют разного.

### Два файла compose и почему их два

`compose.yaml` — для работы на своей машине. `docker-compose.yml` — вариант под ограничения App Platform. Локально `docker compose` берёт `compose.yaml`, потому что при наличии обоих он выигрывает; платформа читает `docker-compose.yml`.

App Platform запрещает в манифесте директиву `volumes`, верхнеуровневый ключ `name` и проксирует основной домен **только на первый сервис**. Поэтому в `docker-compose.yml`: `web` стоит первым, тома убраны, окружение выписано у каждого сервиса целиком вместо YAML-якорей, сервис `tunnel` не нужен. Содержимое переменных у `web`, `bot` и `worker` совпадает с локальным файлом.

### Dockerfile + управляемая база — если данные должны переживать деплой

Платформа берёт `Dockerfile` и поднимает **один** контейнер. Из этого следуют две вещи.

**База нужна отдельная.** Внутри контейнера PostgreSQL нет, а `DATABASE_URL` по умолчанию смотрит на `localhost` — приложение не стартует и отдаёт 502. Нужно создать управляемую базу PostgreSQL и вписать её строку подключения в переменную `DATABASE_URL` в панели:

```
postgres://пользователь:пароль@хост:5432/база
```

Управляемые базы обычно требуют шифрованного соединения и выдают строку с `sslmode=verify-full` — это значит «проверь сертификат базы». Сам сертификат нужно положить в переменную `DATABASE_CA_CERT`: туда годится и текст PEM целиком, и путь к файлу. Без сертификата приложение при старте скажет об этом прямо и предложит второй путь — заменить в строке подключения `sslmode=verify-full` на `sslmode=require`. Тогда соединение останется шифрованным, но подлинность сертификата проверяться не будет.

Строку подключения задавайте **только** переменной окружения. В `app/config.py` её вписывать нельзя: там она попадёт в репозиторий вместе с паролем, а значение из панели всё равно перекроет значение по умолчанию в коде.

**Все три процесса живут в одном контейнере.** Команда по умолчанию в `Dockerfile` — `python -m app.run`. Этот модуль поднимает `web`, дожидается ответа на `/health` (значит схема создана и начальные данные загружены) и только потом запускает `bot` и `worker`. Если падает `web` — контейнер завершается и платформа его перезапускает. Если падает `bot` или `worker` — поднимаются заново с нарастающей паузой, а страницы продолжают открываться: неверный токен бота не должен ронять мини-приложение. Без `MAX_BOT_TOKEN` запускается только `web`.

На работу через compose это не влияет: там у каждого сервиса своя команда, и она перекрывает `CMD` из `Dockerfile` — процессы по-прежнему разъезжаются по отдельным контейнерам.

### Docker Compose — если платить за базу не нужно

Тип приложения Docker Compose поднимает все четыре сервиса сам, `DATABASE_URL` собирается автоматически, ничего дописывать не надо.

Плата за это — **данные не переживают пересборку**. Тома на платформе запрещены, поэтому база живёт внутри контейнера: при каждом деплое пропадают пользователи, подписки и напоминания, а начальные данные загружаются заново. Для демонстрации это терпимо, для работы с живыми людьми — нет.

### Что выбрать

| | Dockerfile + управляемая база | Docker Compose |
|---|---|---|
| Данные после деплоя | сохраняются | стираются |
| База | отдельная услуга, платная | внутри приложения |
| Домен | сохраняется, если приложение уже создано | новый, приложение создаётся заново |
| Правки в коде | нужен `app/run.py` (уже в репозитории) | не нужны |

### Что проверить после деплоя

```bash
curl -i https://ваш-домен.twc1.net/health
```

`{"ok":true}` — база на месте и схема применена. Если база недоступна, ответ будет `{"ok":false,"db":"…"}` с причиной прямо в теле, но статус останется 200: иначе платформа считает контейнер больным и валит весь деплой, не дав ничего рассмотреть.

Полная картина — на странице `/__diag`:

```
https://ваш-домен.twc1.net/__diag
```

Там видно метку сборки, порт, адрес базы без пароля, состояние подключения с причиной отказа, состояние дев-входа и список переменных окружения — только имена и пометка «задана / задана, но пустая / не задана», значения не печатаются. По ней сразу понятно, доехала ли переменная из панели и не перебила ли она настройки.

**Приложение не падает из-за базы.** Если при старте подключиться не удалось, `web` всё равно поднимается, отдаёт `/health` и `/__diag`, показывает на остальных страницах понятный текст вместо ошибки 500 и продолжает пробовать подключиться каждые 15 секунд. Как только база отвечает — схема применяется, начальные данные грузятся, страницы начинают работать, и всё это без перезапуска контейнера.

Первая же строка `[db] подключаюсь к …` называет пользователя, хост, порт и базу — пароль в лог не пишется. По ней видно, доехала ли строка подключения: если там `localhost`, значит переменная пустая или названа иначе. Дальше приложение не молчит минуту, а сразу говорит причину словами: неверный пароль, нет такой базы, нет сертификата, сертификат не читается, сертификат не прошёл проверку.

В логах при старте должны быть строки `[run] web отвечает, схема на месте`, `[run] запускаю bot`, `[run] запускаю worker` и `[web] сборка <метка>`. Метка сборки показывает, какая версия реально запущена.

И отдельно: `ALLOW_DEV_AUTH` на публичном адресе должен быть `false`. Иначе войти можно по любому номеру без подписи MAX — включая номера администраторов.

## Переменные окружения

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `MAX_BOT_TOKEN` | да | — | Токен бота. Без него поднимается только `web` |
| `MAX_BOT_USERNAME` | да | — | Ник бота без `@` |
| `ADMIN_USER_IDS` | нет | — | `user_id` администраторов через запятую |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | нет | `aperio` | База, которую поднимает `compose` рядом |
| `DATABASE_URL` | только при одном контейнере | `postgres://aperio:aperio@localhost:5432/aperio` | Готовая строка подключения к внешней базе. В `compose` собирается сама |
| `DATABASE_CA_CERT` | только при `sslmode=verify-*` | — | Корневой сертификат управляемой базы: текст PEM или путь к файлу |
| `APP_PORT` | нет | `8080` | Порт на хосте |
| `ALLOW_DEV_AUTH` | нет | `false` | Вход без подписи MAX по любому номеру. Только локально: на публичном адресе открывает админку посторонним |
| `INIT_DATA_TTL_SEC` / `SESSION_TTL_SEC` | нет | `3600` / `86400` | Срок данных запуска и сессии |
| `ADMIN_SESSION_TTL_SEC` | нет | `7200` | Срок сессии администратора — короче, токен виден в адресе |
| `DEMO_DELAY_SEC` | нет | `60` | Задержка демо-окна |
| `WORKER_INTERVAL_SEC` | нет | `15` | Период планировщика |
| `SEED_ON_START` | нет | `true` | Начальные данные в пустую базу |

Порты: `web` — 8080 (наружу `APP_PORT`), `db` — 5432 (не публикуется), `bot` и `worker` портов не слушают. Зависимости и версии — в `requirements.txt`.

## Сборка

Образ один на три процесса, база — официальный `postgres:16-alpine`. Все 32 зависимости ставятся готовыми колёсами (`py3-none-any` либо `manylinux x86_64`), компилировать при установке нечего: около 15 МБ загрузки поверх `python:3.12-slim`. На обычном канале сборка укладывается в минуту — с запасом к пятиминутному лимиту, который ставит регламент.

Версия Python зафиксирована не случайно: `maxo 0.9.0` требует `>=3.12,<3.15`, поэтому базовый образ — именно `python:3.12-slim`.

## Данные

Авторизация — по подписи `initData` из MAX. Дальше сессия живёт в подписанном токене: он ставится cookie и одновременно подставляется в адрес (`?s=…`), потому что во встроенном окне MAX сторонние cookie могут быть заблокированы. Токен проверяется подписью и истекает через `SESSION_TTL_SEC`. Храним: `user_id`, имя, категорию льготы, фильтр, подписки, напоминания.

Уведомления идемпотентны: ключ пишется до отправки, бронь снимается только при отсутствии связи.

Начальные данные (`app/seed_data.json`): 20 площадок, 17 льготных правил и 7 окон записи по Москве. Правила собраны по официальным страницам музеев и mos.ru, у каждого указан источник и дата проверки; перед показом пользователям их стоит сверить заново. Даты окон записи строятся от момента первого запуска, чтобы в демонстрации всегда были и открытая, и предстоящая запись. Загружаются только в пустую базу — для перезалива `docker compose down -v`.

## Порядок работы с тестовыми данными

Отдельного «тестового режима» нет: приложение всегда работает с одной базой. Тестовым делает данные их источник, и источников три.

**1. Начальный набор `app/seed_data.json`** — то, что видит проверяющий сразу после `docker compose up --build`. Загружается при старте `web`, если таблица `venues` пуста (переключатель `SEED_ON_START`, по умолчанию `true`). Площадки и льготные правила — настоящие, со ссылкой на источник и датой сверки в каждой записи. Даты окон записи считаются от момента первого запуска, поэтому в ленте всегда есть окно с открытой записью, окно «скоро откроется» и закрывшееся — независимо от того, в какой день проверяют.

Перезалить набор: `docker compose down -v && docker compose up --build`. Правка записи руками сохраняется до следующего `down -v` — миграции данные не трогают.

**2. Проверочные объекты из админки** — кнопки на экране «Админка»:

| Кнопка | Что создаёт | Что произойдёт |
|---|---|---|
| «Окно: запись через минуту» | Окно записи с `reg_opens_at = now + 60 с` | Через минуту `worker` разошлёт уведомление всем, у кого подписка совпала с фильтром |
| «Льготный день на завтра» | Льготное правило на завтрашний день недели | Уведомление о льготном дне уйдёт ближайшим проходом (с 10:00 до 21:00 МСК) |

Такие записи ничем не отличаются от обычных: их видно в каталоге, можно отредактировать и удалить в той же админке. Удаление окна уносит за собой напоминания по нему.

**3. Личное демо-окно `/demo`** — команда боту или кнопка «Прислать тестовое уведомление» в профиле. Создаёт окно с полем `demo_for = ваш user_id`: уведомление придёт только вам и не побеспокоит остальных. Задержка — `DEMO_DELAY_SEC`, по умолчанию 60 секунд.

Чего в базе нет и не будет: выдуманных площадок и выдуманных льгот. Если запись нельзя подтвердить ссылкой на сайт музея или mos.ru, она в набор не попадает — у каждой строки `seed_data.json` есть `source_name`, `source_url` и `checked_at`.

## Проверка

1. `/start` → «Открыть Aperio» → категория «Студент вуза или колледжа».
2. Главная: льготные дни и окна записи.
3. Каталог → «Фильтры» → «Экскурсии» → «Показать события» → «Уведомлять о таком».
4. Карточка события → сердечко → «Позвать компанию».
5. Профиль → «Прислать тестовое уведомление» → через минуту сообщение в чате.

### Проверка без бота MAX

Интерфейс и админку можно посмотреть на своей машине, не создавая бота: сервису `web` токен не нужен.

```bash
cp .env.example .env
# в .env:  ALLOW_DEV_AUTH=true  и  ADMIN_USER_IDS=1
docker compose up --build db web
```

Открыть `http://localhost:8080/`, ввести номер `1` — это вход администратора. Доступны все экраны и админка. Бот и уведомления в этом режиме не работают: для них нужен токен.

`ALLOW_DEV_AUTH=true` допустим только на `localhost`. На публичном адресе он позволяет войти под любым номером, включая номера администраторов; при таком сочетании `web` пишет предупреждение в лог.

### Проверка уведомлений

Уведомления требуют бота: заполнить `MAX_BOT_TOKEN` и `MAX_BOT_USERNAME`, поднять всё (`docker compose up --build`), адрес мини-приложения взять из логов `tunnel`.

1. Канал «избранное»: в боте `/demo` — через 60 секунд придёт уведомление об открытии записи.
2. Канал «подписка»: сохранить подписку в «Фильтрах», затем в админке нажать «Окно: запись через минуту».
3. Канал «льготный день»: в админке нажать «Льготный день на завтра» (сообщение уходит с 10:00 до 21:00 МСК).

Проверочные объекты удаляются из админки как обычные записи.

## Примеры ожидаемого поведения системы

Что именно должно произойти в ответ на действие. Слева — что делает человек, справа — что обязано случиться; если случилось другое, это ошибка.

### Бот

| Действие | Ожидаемый результат |
|---|---|
| `/start` впервые | Приветствие и кнопка «Открыть Aperio». В `users` появляется строка с `user_id` и именем |
| `/start` повторно | То же сообщение; второй строки в `users` не появляется |
| `/demo` | Ответ «пришлю через минуту», через `DEMO_DELAY_SEC` — уведомление об открытии записи. Другим пользователям оно не приходит |
| `/demo` дважды подряд | Два разных демо-окна, два уведомления: ключ идемпотентности содержит id окна |
| `/admin` | Бот ждёт текст вопроса; следующее сообщение уходит всем главным администраторам с кнопкой «Ответить» |
| `/reply 123 текст` от главного администратора | Ответ уходит пользователю 123, администратор получает подтверждение. От остальных — отказ |
| `/help` | Короткая подсказка по командам |
| Произвольный текст вне режима вопроса | Подсказка с кнопкой «Открыть Aperio», а не молчание |
| Пользователь заблокировал бота | Отправка возвращает 403/404 → `users.blocked = true`, больше ему не пишем |

### Мини-приложение

| Действие | Ожидаемый результат |
|---|---|
| Запуск из MAX | `initData` проверяется по HMAC-SHA256, выдаётся сессионный токен. Подпись не сошлась или старше `INIT_DATA_TTL_SEC` → 403 и экран входа |
| Первый запуск | Онбординг с выбором льготной категории; «Пропустить» тоже допустим — лента покажет всё |
| Главная | Льготные дни и окна записи, отсортированные по дате. Окна с закрытой записью остаются видимыми, пока само событие не прошло |
| Поиск и «Показать события» | Страница перезагружается с результатом и **не** выбрасывает на экран входа: токен уходит скрытым полем, потому что GET-форма отбрасывает строку запроса из `action` |
| Сердечко на карточке | Запись появляется в «Избранном» и в «Уведомлениях»; повторное нажатие снимает |
| Ползунок в «Уведомлениях» | `reminders.muted` переключается, событие остаётся в списке, сообщения по нему не уходят |
| «Уведомлять о таком» в фильтрах | Текущий фильтр сохраняется в `subscriptions` как JSON; в форме админки видно, скольких человек он охватывает |
| Событие прошло | Уходит из «Избранного» в «Прошедшие события» |
| «Позвать компанию» | В MAX — окно выбора чата со ссылкой на карточку; вне MAX — ссылка копируется в буфер |
| Открытие по ссылке с `start_param` | Сразу карточка события, минуя онбординг |
| Токен старше `SESSION_TTL_SEC` | Экран входа, а не ошибка 500 |
| Несуществующий адрес | Страница 404 в оформлении приложения |

### Уведомления

| Ситуация | Ожидаемый результат |
|---|---|
| Наступил `reg_opens_at` | В течение `WORKER_INTERVAL_SEC` (по умолчанию 15 с) сообщение уходит тем, у кого событие в избранном или совпала подписка |
| `worker` перезапустился после отправки | Повтора нет: ключ `reg_open:w<id>` уже в `notifications` |
| Связи с MAX не было | Бронь ключа снимается, сообщение уходит следующим проходом |
| Окно создано с уже прошедшим `reg_opens_at` | Уведомление уйдёт, если открытие было не раньше 24 часов назад и запись ещё не закрылась |
| До закрытия записи меньше 24 часов | Напоминание только тем, у кого событие в избранном, и только если окно длилось больше 36 часов — иначе это дубль сообщения об открытии |
| Событие завтра | Напоминание тем, у кого оно в избранном |
| Завтра льготный день | Сообщение тем, чья категория совпала с правилом, в промежутке с 10:00 до 21:00 МСК — ночью не пишем |
| Льгота не подходит пользователю | Уведомления нет: `eligibility`/`categories` сверяются с `users.category` |

### Админка

| Действие | Ожидаемый результат |
|---|---|
| Обычный пользователь открывает `/admin` | Переадресация на главную; ни формы, ни сообщения об ошибке он не видит. Пункта «Админка» в профиле у него тоже нет |
| Главный администратор | Полный доступ, включая «Редакторы» |
| Редактор | Окна и льготные дни ведёт, экран «Редакторы» ему недоступен |
| Редактор открывает `/admin/people` | Переадресация на `/admin`: выдавать и снимать доступ может только главный администратор |
| Создание, правка, удаление записи | Строка в журнале правок: кто, что, когда. Название хранится снимком, поэтому удалённая запись остаётся читаемой |
| Сохранение окна с открытием в прошлом | Уведомление уходит ближайшим проходом, повторно по тому же окну — нет |
| Сессия главного администратора старше `ADMIN_SESSION_TTL_SEC` | Требуется повторный вход, даже если обычная сессия ещё была бы жива: токен виден в адресной строке, поэтому у главных администраторов срок короче |
| `/reply` от обычного пользователя | Отказ. Рассылать сообщения от имени бота может только главный администратор |

## Интерфейс

Вёрстка по макетам команды; иконки и логотип — в `app/static`. Адаптация: 320, 390, от 700 (две колонки) и от 1024 px (три колонки), учёт вырезов через `env(safe-area-inset-*)`.

Шрифт Gilroy коммерческий, файлы в репозиторий не включены (`.gitignore` исключает `app/static/fonts/*.woff`): положите `Gilroy-Light/Regular/Medium/Bold/Heavy.woff` в `app/static/fonts/`. Без них интерфейс переходит на системный шрифт — вёрстка не ломается, но начертания другие.

**Важно при деплое.** App Platform собирает образ из репозитория, поэтому на боевом адресе шрифта не будет, пока файлы не попадут в сборку. Три варианта: включить `.woff` в репозиторий, если лицензия это позволяет; заменить Gilroy на свободный геометрический гротеск с кириллицей (Onest, Manrope, Golos Text — лицензия OFL разрешает и правку, и распространение), поправив пять правил `@font-face` в начале `app/static/css/app.css`; либо оставить системный шрифт. Решение принимает команда — оно влияет на внешний вид, а не на работу приложения.

## Админка

Две роли. **Главные администраторы** заданы в `ADMIN_USER_IDS` — их список правится только на сервере, через интерфейс снять их нельзя. **Редакторы** ведут окна записи и льготные дни, но не выдают доступ другим; их добавляет главный администратор на экране «Редакторы» по `user_id` в MAX, без перезапуска контейнера. Номер будущего редактора главный администратор видит в таблице `users` (`docker compose exec db psql -U aperio -d aperio -c "select id, first_name from users"`) или в журнале правок. Самостоятельной регистрации администратора нет ни в одном виде.

Сводка, ведение окон записи и льготных дней, охват подписчиков прямо в форме, кнопки проверки уведомлений, журнал правок (`/admin/log`): кто создал, изменил или удалил запись и когда. Названия в журнале хранятся снимком, поэтому удалённые записи остаются читаемыми. Если время открытия уже прошло, уведомление уйдёт в течение `WORKER_INTERVAL_SEC` после сохранения; повторно по тому же окну не отправляется.

## Ограничения

- Окна записи заводятся вручную по анонсам: момент открытия записи не публикует ни один открытый источник. Набор «события» Минкультуры заморожен с 2021 года, событийные наборы data.mos.ru — отчётные выгрузки на несколько десятков записей.
- Нет дублирования окна и повторения окон по правилу — повторяющееся событие заводится заново.
- Long polling вместо webhook; бот рассчитан на один экземпляр.
- `shareMaxContent` работает только по клику; вне MAX ссылка копируется в буфер.
- Часовой пояс — Москва.
